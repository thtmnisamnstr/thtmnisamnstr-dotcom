## Search and deployment boundary

The production wrapper runs only when `NETLIFY === 'true'` and `CONTEXT === 'production'`. Ambient values can therefore turn an ordinary `corepack npm run verify` into an indexing build. Inspect their presence without revealing other environment values, and explicitly run local checks with `NETLIFY=false CONTEXT=dev`. Local development, CI and deploy previews must not write production search indexes. Do not set production flags just to make a test resemble production. `corepack npm run reindex` calls `reindexAll()` directly and is not guarded by that condition; use only for an authorized index refresh with the intended site/index/namespace verified.

The known config uses site URL `https://thtmnisamnstr.com`, namespace prefix `thtmnisamnstr-dotcom`, and a `blog` search sourced from `data/blog/**/*.{md,mdx}`. Check current package docs/implementation when upgrading; do not assume hooks, result shapes, filtering, or cleanup semantics remain unchanged.

At the September 2026 audit, `package.json` and the lock requested `nextjs-pinecone-search@^0.1.0`, but the npm registry no longer returned version `0.1.0`; a clean install received `E404`. Treat this as a recorded reproducibility blocker to recheck, not a permanent fact. Resolve it through a maintained published release or an intentional immutable source and verify its package contents/API. Do not substitute an unpinned repository branch merely to make installation proceed.

Rechecked September 28, 2026: a clean npm 12.1.0 install retrieves the current lock, including `nextjs-pinecone-search@0.1.1`; the earlier 0.1.0 E404 is historical and no longer blocks reproducible installation. `corepack npm audit` reports zero findings. All 46 direct dependencies match the latest versions in their declared ranges. TypeScript 7.0.2 is the latest major, but `@typescript-eslint/parser@8.70.1` peers only with TypeScript `<6.1`; TypeScript 6.0.3 is latest in the supported line, and TypeScript 7 has not shipped a programmatic API for the repository’s MDX tooling. `@types/node@24.19.0` is retained because the deployed runtime is Node 24; current Node 26 type definitions would describe a different runtime. Microsoft documents the TypeScript 6 requirement for MDX workflows: https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/.

Node 24.21.0 remains the latest Node 24 LTS release. The package now pins npm 12.1.0 through `packageManager`; GitHub Actions selects it with Corepack, and Netlify has `NPM_VERSION` in `netlify.toml`. npm 12.1.0 supports Node 24.15 and later. The configured Node pin is read from `.nvmrc`; the Netlify account’s separate UI setting remains unverified.

The environment template lists `PINECONE_API_KEY`, `PINECONE_DENSE_INDEX`, `PINECONE_SPARSE_INDEX`, Segment public keys, and Netlify CLI identifiers/tokens. Report presence/scope only; never print secret values. A missing-key build check does not establish successful production search. Source scans alone do not establish whether drafts are indexed.

The reindex script imports the directly declared `@next/env`; keep it compatible with Next. The lockfile is marked `-diff` in `.gitattributes`; inspect it as JSON even when Git displays a binary-style change.

## Quality gates and limitations

`corepack npm run verify` runs lint, typecheck, unit/integration tests, production build, feeds, and sitemap. CI runs workbench/axe checks on 3015, then launches a server on 3012 and runs `BASE_URL=http://localhost:3012 corepack npm run test:e2e:crawl`. Workbench checks can use an already-started production server via `BASE_URL`; otherwise their config starts and stops one. Use an available port, a readiness check, and cleanup of the specific server process started for this task. When a user has a live development preview, build in an isolated source copy/worktree so competing dev/build processes do not overwrite the same `.next` directory.

Some task environments apply an install-script allowlist and may warn during `corepack npm ci`. Do not suppress or ignore a warning that prevents a required executable from working; if the clean install and build succeed, record it as an environment policy warning rather than misclassifying it as an application failure.

As of this review, Next.js 16.3.6 is the latest published active-line patch and `corepack npm audit` reports no known advisories. The Next.js maintainers have announced a scheduled September 30, 2026 release (16.3.7/15.5.27) addressing nine vulnerabilities, including one critical. Recheck and apply the 16.3.7 patch immediately after publication; it is not yet available in the current registry.

The current crawl checks browser page errors and broken/failed images. It does not assert navigation HTTP status, search interaction, redirects, canonical URLs, external links, all lazy images, or visual layout. Supplement it with targeted checks for changed behavior; do not describe it as exhaustive.

`.lighthouserc.json` takes three runs each for `/`, `/blog`, a historical image-rich article, `/about`, and `/resume`, requiring performance 0.8 and accessibility/best-practices/SEO 0.9. Keep these thresholds unless the user requests a policy change. Theme/logo performance regressions and run-to-run variation were explicitly fixed in February 2026. The README screenshot lives under `docs/images`, outside runtime assets; refresh it when the visible shell changes substantially.

The checked-in Lighthouse autorun config uploads reports to temporary public storage. For ordinary local validation, use its installed/configured CLI version and run `collect`, then `assert` separately against `.lighthouserc.json`; do not run `upload`. Equivalently, use a temporary config with upload targeting filesystem while preserving URLs, runs and assertions. Explicit authorization to publish reports or existing CI behavior can justify the original autorun command.

The image optimizer rewrites matching images throughout `public` and `src/assets`; the clean script removes `node_modules`, generated outputs and caches broadly. Read current scope and use the clean script's dry-run option before considering it during a targeted fix. Lint's existing glob excludes root configs, tests and `data`, so a passing lint result does not by itself validate every maintenance edit.
