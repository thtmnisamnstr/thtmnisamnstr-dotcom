## Establish what is actually outdated

- Record Node/npm versions, `.nvmrc`, package engines, CI runtime, Netlify configuration and lockfile state. Check whether `node_modules` matches the lock before attributing failures to the code. An installed Node outside the declared engine range is not a valid baseline just because it is newer.
- Query current npm metadata for all direct production and development dependencies (`npm outdated --json`, plus `npm view` where useful). Compare installed, wanted, and latest stable versions: `npm update` alone misses upgrades beyond declared ranges. Check `npm audit --json` and `npm ls --depth=0`; their nonzero exits can be findings, not command failures. Run or capture these commands independently rather than losing their JSON in an `&&` chain. Separate actual network/authentication errors from findings; on registry throttling, use a bounded retry and report an incomplete check rather than treating stale or partial metadata as current.
- Confirm every locked direct dependency is still retrievable before trusting the existing installation. If a package/version was unpublished, identify the maintained authoritative distribution or replace it deliberately; do not silently switch to an unpinned Git branch or preserve a working `node_modules` tree that `npm ci` cannot reproduce.
- Inspect transitive vulnerabilities and stale packages through their parent dependencies, as well as tools pinned outside dependencies: inline Lighthouse CLI versions, GitHub Actions, Playwright browser compatibility, the Netlify adapter, build plugins and documented setup commands. Include deprecations and obsolete config exposed by these updates. Do not promise every transitive package can independently use its latest major.
- Verify release status and migration requirements from current primary sources. For Node, default to the newest supported LTS line and its latest patch suitable for Next/Netlify; explain this choice. If the user explicitly requests Current, use it when supported and clearly report any platform incompatibility. Never freeze today's versions into this skill.
- Run a meaningful baseline using the repository-supported runtime and lockfile where possible. Record pre-existing failures so they are not confused with new regressions. If the selected Node is installed but not on the default `PATH` (for example, a keg-only package-manager installation), scope that runtime's `bin` directory to the task command instead of changing the system default. Do not overwrite another task's active dependency installation/build; use suitable isolation when necessary.

## Implement updates

- Update all applicable direct dependencies, including major versions with the needed migrations. Group coupled updates such as Next/React, Tailwind/PostCSS, ESLint/TypeScript tooling, and test/browser tooling so incompatibilities can be diagnosed. Keep React and React DOM aligned.
- Use the existing npm lockfile. Regenerate it with npm after manifest changes, then verify a clean `npm ci` under the selected runtime. Inspect unexpected local/workspace/file dependencies and large lockfile churn; preserve intended dependencies and remove stale entries through package-manager resolution.
- Update `.nvmrc`, `package.json` engines, CI Node selection, and README together. Inspect Netlify runtime overrides when accessible; report unverified dashboard settings rather than claiming they are synchronized. Use the existing version manager for this project/session; do not replace system Node or modify unrelated projects' defaults.
- Update npm itself only to a release supported by the selected Node and task environment. Respect an existing `packageManager` field if one is introduced. Keep `@types/node` compatible with the deployed runtime rather than blindly advertising unavailable runtime APIs. A direct package that deliberately remains behind its newest major because of the selected runtime or a peer-tool ceiling is a documented compatibility constraint, not an unexplained omission.
- Read official migration guides and adapt configuration/code. In particular, keep the Pages Router, MDX pipeline, webpack requirement, theme behavior, image handling, feed/sitemap output, search API, and Netlify deployment functioning. A dependency update is not an automatic request to migrate routing architecture.
- Fix dependency security findings through compatible updates and necessary code changes. Do not use `--force`, `--legacy-peer-deps`, disable checks, or lower performance thresholds simply to get a green result. If latest stable is blocked, attempt a supported path and document the exact dependency/platform constraint and retained version.
- Treat broken links, metadata drift, content correctness, provider account configuration, and expiring services as separately assessable findings. Fix maintenance-related source defects within scope; do not invent biographical facts, renew paid services, rotate credentials, or expand to unrelated content imports.

## Verify and deliver

Under the chosen Node version, run `npm ci`, then inspect ambient `NETLIFY` and `CONTEXT` without printing secrets. For local checks, run `env NETLIFY=false CONTEXT=dev npm run verify`, a production-server sitemap crawl, and the existing Lighthouse assertions using local-only report output as described in the reference. This explicit override prevents the production-only Pinecone wrapper from activating; use a genuine production build only when production indexing is authorized and intended. Inspect mobile/desktop light/dark pages and the search flows. The available `$verify-site` skill supplies the detailed release checklist. During an upgrade, use targeted checks while migrating and one final full suite after the last change; if `$verify-site` is subsequently invoked against the unchanged sources, lockfile, and runtime, reuse that final evidence instead of duplicating expensive suites.

Re-run the outdated/audit/install-tree checks after upgrades. The result should identify each remaining direct dependency that is behind latest stable and why, and any remaining vulnerability with affected path, relevance, and available fix/blocker. Record unresolved external configuration checks separately from passing local checks.

Deliver a concise before/after version summary, migrations/fixes, verification results, and exact remaining constraints. Only claim the site is fully updated when supported updates are actually applied and checks pass; distinguish ready locally, pushed, and deployed states.
